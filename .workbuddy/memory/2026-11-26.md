- `LoginView.vue`：废弃左右分屏（删 login-brand 整块 + login-panel），改全屏 `.login-bg` 动态层 + `.login-stage` 居中主体（logo + DataPro 标题 + 玻璃登录卡）。删除全部品牌文字要点（只读·安全/先口径·后取数/全程留痕）、login-tag、login-card-head（登录+chip）、演示 label、版权脚注；仅保留 logo/标题/账号密码/进入按钮/admin·analyst。图标 import 精简为 Hide/Lock/User/View。
- `style.css` 重写登录样式块：三类纯 CSS 背景动画——`meshDrift`（网格 28s 平移）、`orbFloatA/B/C`（三团光斑 19/24/30s 错峰漂移，钴蓝+暖琥珀+灰蓝）、`scanSweep`（扫描光带 11s 下扫）；明暗各有配色。登录卡居中玻璃，演示 chip 也玻璃化。暗色下 Element Plus 输入框默认白底突兀 → 加 `[data-theme="dark"] .login-card .el-input__wrapper` 深色玻璃覆盖。
- reduced-motion：关闭 login-page/login-card/login-mark/bg-mesh/bg-orb/bg-scan 动画，保留静态光场。
- 验证：CSS 括号平衡、LoginView.vue SFC 编译通过；用 pw-browser eval 读 computed style 确认动画在运行（orb transform 位移、mesh background-position 33.69px、scan top 743px）；截图 `login-dynamic-light.png` / `login-dynamic-dark.png` 核对居中与光场观感。

### 居中修正（用户反馈「输入框主体没居中，放大缩小都要居中」）
- 实测根因：水平方向本就精确居中（cx 恒=vw/2），但垂直方向 `.login-stage` 整体居中时，logo+标题占布局空间把卡片往下推 72px（1280×720 下 stage cy=360 但卡片 cy=432），用户关注的「输入框卡片」本体不在正中。
- 修法：`.login-mark` 改为 `position:absolute; bottom:calc(100% + 26px); left:50%; translate:-50% 0`（用独立 `translate` 属性避免被 loginUp 的 `transform` 覆盖），使卡片成为 stage 唯一流式内容 → 卡片中心恒=视口中心。加 `@media (max-height:600px)` 矮视口保护：logo 回文档流并缩小，防 overflow 裁切。
- 验证：pw-browser run-code 实测 9 种视口（375×812 ~ 2560×1440），常规视口下卡片 dx=0/dy=0、无横向溢出；矮视口 1366×560 下水平 dx=0、垂直 dy=51（保护规则生效）。截图 `login-dynamic-light.png` 已更新为居中版。

### 登录卡放大 + 真实边缘玻璃折射（用户要求：放大一点/半透明/边缘玻璃形变）
- 放大：stage max-width 400→456，卡片 padding 32/28/26→38/34/32、圆角 20→24、gap 15→18，logo 60→66、标题 38→42、输入框 inner 34→38/字号 15、按钮 48→54/16px、demo chip 加大；小屏与矮视口同步缩放。
- 半透明：新增 `--login-glass-bg`（明 .42 / 暗 .38，比通用卡更透），让背景光斑穿透。
- 边缘折射（关键技术）：`LoginView.vue` 内联 SVG `<filter id="glassEdgeRefract">`（feTurbulence fractalNoise + feDisplacementMap，scale 22）；`style.css` 用双层兄弟伪元素分工——`.login-card::before` mask content-box 只保留内圈做 blur(26px) 磨砂，`.login-card::after` mask exclude 只保留 18px 边缘环带做 `backdrop-filter:url(#glassEdgeRefract)`。**关键**：卡片本体不能带 backdrop-filter，否则边缘层采到已模糊内容、形变不可见。
- 辅助：`.login-stage::before` 聚焦光斑给折射提供可扭曲的明暗素材（径向 mask 淡出消除矩形硬边）；卡片 inset 双重发丝边模拟厚玻璃聚光。

- 验证：CSS 括号平衡、LoginView.vue SFC 编译通过；居中复核 dx=0/dy=0（小屏 dy=6）；截图 `login-dynamic-light.png` / `login-dynamic-dark.png` 已更新为折射终稿。

### 折射方向修正：卡片不变形、只让「透过卡片看到的背景」形变（用户澄清）
- 用户澄清：「登录卡片不用变形，是透过登录卡片看后面的背景有形变」。即卡片矩形轮廓必须规整，形变只发生在背景。
- **关键技术认知（踩坑）**：Chrome 对 `backdrop-filter: url(#svgFilter)` 里的 `feDisplacementMap` 支持有缺陷——用 pw-browser eval 把 scale 极端设到 150，透过卡片的网格纹丝不动；改用**普通** `filter: url(#...)` 作用于一个测试 div，scale=40 时网格立即剧烈波浪弯曲。故**不能靠 backdrop-filter 做真实折射**，必须换成「卡片内放背景镜像层 + 普通 filter」。
- 另两个失败尝试：① feTurbulence 低频（0.01）只产生整体平移，看不出弯折 → 提到 0.014~0.02；② background mesh 原 `--grid-line` 仅 .045 透明度又被 blur 吃掉 → 登录页网格单独提到 .13/.15 且线宽 1.5px，blur 26→3 最终去掉。
- 终稿实现：`LoginView.vue` 内 SVG 只保留单个 `filter#glassRefract`（feTurbulence fractalNoise + feDisplacementMap scale=10，x/y=-20% w/h=140%，**去掉 feComposite**——它会把位移结果裁回原 alpha 抵消形变）；`<form class="login-card">` 首个子节点加 `.card-refract > .card-refract-grid` 背景镜像层。
- `style.css`：`.card-refract`（inset:0, border-radius:inherit, overflow:hidden, z-index:0）裁切保证卡片轮廓不变；`.card-refract-grid` 复制 44px 网格 + `background-attachment:fixed` 与页底对齐 + `filter:url(#glassRefract)` + 径向 mask（92%×88%, 42%实→100%透明）让边缘自然融入；`.login-card > *:not(.card-refract)` 抬 z-index 保证表单清晰。卡片底色调到明 .34 / 暗 .30。
- 验证：亮/暗截图确认——卡片轮廓规整、卡片内网格轻微波浪弯曲且与外侧连续、表单可读；SFC 编译 + CSS 括号平衡通过。截图 `login-refract-final2-light.png` / `login-refract-final2-dark.png`。中途调试图 `login-refract-debug*.png` / `filter-mintest.png` 仅验证用，非交付稿。

### 登录框浮动标签（用户澄清：不是 bug，是 floating label 需求）

## 关于「切片（Chunking）」的核查与一处修复

结论：**项目里没有切片这一层**（全仓 grep 无 chunk/split 语义），检索粒度是「一条元数据 = 一份文档」：
- 表 → 1 文档（中文名 + 描述 + 关键词 + 前 30 列），口径 → 1 文档（名 + 别名 + 定义），知识条目 → 1 文档
- `data/vector_docs.jsonl` 实测 53 条（11 表 / 14 口径 / 28 知识），表文档平均 176 字、最长 261 字
- 上传文件（F27）解析成真实 MySQL 临时表，检索的是表级描述，**不切行、不切文本**
- 不切片是对的：把「表名+描述+关键词+字段」切开，生成阶段拿不到完整字段就会编字段；176 字的文档本来就在一个语义单元内

发现并修掉的真实缺陷：**同一份文档有两套文本**
- `vector_recall._table_text` = `cn_name + description`；`export_vector_docs` 却额外含 keywords + 前 30 列
- 后果：`VECTOR_BACKEND=memory` 与 `milvus` 两种部署召回结果不同，且不报错、线上极难发现
- 修法：文本构造函数收口到 `vector_recall.table_doc_text/caliber_doc_text/knowledge_doc_text`，导出脚本直接复用；knowledge 文本补上 `formula`（用户常问「怎么算」）
- 顺带明确：列放在文本**最后**并且只取前 30 个——编码窗口默认 128 token，实测最长 261 字会被截尾，必须让描述与关键词在前面

验证：`tests/test_vector_docs.py`（5 项，断言两链路文本完全一致、宽表列截断且列在末尾）；全量 **287 passed / 49 个文件**；真实数据核对 `docs[0].text == table_doc_text(tables[0])`。

未做（属可选优化，需拍板）：字段级检索（冷门字段只有落在 description/keywords 才命中）、`knowledge` 文档灌了 Milvus 但检索端从不查 `type=knowledge`（`knowledge_base.match` 走子串）、`vector_max_length=128` 对 261 字文档偏小（提到 256 需重测召回基线）、无 PDF/Word 长文档摄取。

## 字段级检索（二级字段文档）落地

### 设计
- 二级文档：`type=column`、`uid=column:{table}.{col}`，文本 = 表名 + 表中文名 + 列名 + 列中文名 + 类型 + 业务提示（`common_pitfalls`，例如「一单可能多商品」）。**不写 sample_values 与 is_pii**：编码后会持久化进 Milvus，等于把业务数据带出边界。
- 单一来源：`vector_recall.flatten_columns()` 摊平（补 table_name/table_cn）+ `column_doc_text()` 构造文本，检索与灌库共用（延续上一轮「两套文本会漂移」的教训）。
- 两套命中规则，**不可混用**：
  - `_column_hits`：全名 / 英文整词（`(?<![a-z0-9_])`）→ 用于**表补位**。
