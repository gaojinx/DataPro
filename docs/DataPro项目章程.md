> **基线假设（评审时确认）**
> 1. 目标用户：以业务人员自助取数为主场景，分析师提效为次场景
> 2. 数据源：MySQL 数仓为主，后续扩展 Excel / BI 平台

## 1. 背景与问题

- 业务人员取数依赖数据团队排期，平均等待周期长，高频简单需求占比高
- 数据口径不统一，同一指标不同人算出不同结果
- 数据质量依赖人工巡检，问题发现滞后

**核心主张**：用一个受控的数据管家 Agent，承接高频、规则明确的取数与数据问答需求，让数据团队聚焦复杂分析。

## 2. 项目目标与成功标准

### 2.1 业务目标（北极星）
MVP 上线 3 个月内，承接业务取数请求 ≥ 30%，数据团队此类工单量同比下降 ≥ 30%。

### 2.2 质量指标（验收门禁）

| 指标 | 定义 | 门槛 | 性质 |
|---|---|---|---|
| SQL 可执行率 | 生成的 SQL 能成功执行的比例 | ≥ 95% | 阶段门禁 |
| 结果正确率 | 人工抽检结果与预期一致的比例 | ≥ 90% | 阶段门禁 |
| 幻觉率 | 编造字段/表/口径的比例 | ≤ 2% | 一票否决 |
| 拒答恰当率 | 应拒答场景中正确拒答的比例 | ≥ 95% | 阶段门禁 |
| 平均响应时长 | 从提问到返回结果 | ≤ 30s（P90） | 观察项 |
| 人工介入率 | 需人工接手的会话比例 | 持续下降 | 观察项 |

**设计原则**：宁可明确说"我不确定/需要人工"，绝不返回看似正确的错误数据。

## 3. 范围定义

### 3.1 MVP 包含（In Scope）
1. **自助取数（Chat2SQL）**：自然语言 → SQL → 结果表格，支持追问与修正
2. **元数据问答**：表/字段含义、口径说明、表血缘查询
3. **数据质量巡检（简化版）**：核心表空值率、断流检测、日级自动巡检+告警

### 3.2 明确排除（Out of Scope / 负面清单）
- ❌ 任何写操作：不自动 INSERT / UPDATE / DELETE / DDL
- ❌ 权限外数据：不返回用户无权限的行/列，不脱敏绕过
- ❌ 大结果集直出：超过阈值（如 1 万行）仅返回摘要 + 导出任务转人工审批
- ❌ 跨库联邦查询、实时流数据（二期再议）
- ❌ 自由生成报告结论（只给数据，不给业务判断，避免幻觉误导）

### 3.3 用户与权限模型
- Agent 以**模拟登录用户身份**执行查询（不使用共享高权限账号）
- 行/列级权限由数据源侧透传，Agent 不做权限判断二次实现
- 全链路审计：谁、问了什么、执行了什么 SQL、返回了什么、耗时

## 4. 技术方案概要

| 层 | 选型 | 说明 |
|---|---|---|
| LLM | 国产 API 或私有化模型 | 数据不出域为前提，评审时按公司安全要求定 |
| 编排 | 自研状态机（优先）或 LangGraph | 取数流程固定：澄清 → 召回 → 生成 → 校验 → 执行 → 呈现 |
| Schema 召回 | 向量检索 + 关键词混合 | 先召回相关表结构/口径再生成 SQL，不把全库 Schema 塞给模型 |
| SQL 校验器 | 自研规则引擎 | 执行前检查：语法、权限、表名/字段存在性、扫描量预估 |
| 知识库 | 指标口径库 + 字段字典 + 历史问答对 | 治理优先于检索算法 |
| 评测 | 自建评测集 + 回归流水线 | 先建评测集再写业务代码 |

### 4.1 技术栈清单（详细）

| 分类 | 组件 | 建议选型 | 备选 | 选择理由 / 备注 |
|---|---|---|---|---|
| **模型层** | 主对话/SQL 生成 LLM | DeepSeek-V3 API | Qwen-Max、私有化 Qwen/GLM | 代码与 SQL 能力强，成本可控；**待安全评审定** |
| | Embedding 模型 | BGE-M3（本地部署） | text-embedding-v3 API | 元数据召回用，本地部署避免数据出域 |
| | Rerank | BGE-Reranker | — | 召回后精排，提升 Schema 命中率 |
| **应用层** | 后端框架 | Python 3.11 + FastAPI | Java Spring AI（团队 Java 强则选） | LLM 生态成熟、异步友好；最终以团队技能栈为准 |
| | LLM 开发框架 | 原生 SDK（openai 兼容协议） | LangChain / LangGraph | 流程固定，优先自研状态机；框架仅按需引入 |
| | SQL 解析与校验 | sqlglot | — | 语法校验、AST 分析、方言转换、表/字段提取 |
| | 数据库连接 | SQLAlchemy + PyMySQL | — | 连接池管理，只读账号，模拟用户身份透传 |
| **数据层** | 业务库/审计库 | MySQL 8.x | — | 会话记录、审计日志、任务管理 |
| | 向量库 | Milvus | PGVector、Elasticsearch | 元数据/口径/问答对召回；小规模可先用 PGVector 降本 |
| | 缓存 | Redis | — | Schema 缓存、会话上下文、限流 |
| **知识治理** | 口径库管理 | MySQL 结构化表 + Git 版本化 | — | 口径变更可追溯，与代码库一起走 MR 评审 |
| | 元数据采集 | 自研采集脚本（Information Schema） | Atlas、OpenMetadata | MVP 只需表/字段/注释，不自建元数据平台 |
| **评测** | 评测框架 | pytest + 自建评测集（JSONL） | Ragas、DeepEval | 指标自定义（可执行率/正确率/幻觉率），CI 回归 |
| | 数据集管理 | JSONL + Git | — | 评测集随代码版本化管理，与 Prompt 同步变更 |
| **前端** | Web 界面 | Vue 3 + Element Plus | React + Ant Design | 对话式取数界面 + 结果表格 + 导出；以团队技能栈为准 |
| **基础设施** | 部署 | Docker Compose（MVP）→ K8s（扩量后） | — | MVP 单机可跑，不提前上 K8s |
| | 可观测 | Prometheus + Grafana + Loki | SkyWalking | 指标：QPS、时延 P90、各节点失败率、LLM token 消耗 |
| | 全链路追踪 | 会话级 trace_id 贯穿（结构化日志） | Langfuse | 记录每次召回/生成/校验/执行明细，支撑幻觉归因 |
| **安全** | 脱敏 | 按脱敏规则清单在返回层拦截 | 数据库侧动态脱敏 | 返回层兜底，双保险 |
| | 审计 | MySQL 审计表 + Loki 日志 | — | 谁、问了什么、SQL、返回摘要、耗时，保留 ≥ 180 天 |

**选型原则**：
1. 数据不出域：Embedding/Rerank 必须可本地部署；LLM 部署方式待安全评审
2. 框架最小化：流程固定优先自研状态机，避免 LangChain 全家桶带来的调试黑盒
3. 待评审项：后端语言（Python vs Java）、前端框架、向量库规模——均以**现有团队技能栈**优先，避免为新技术栈付学习成本
4. 所有「备选」在 G1 架构评审时一次性敲定，写入 HLD 后不再摇摆

## 5. 前置依赖（开工前必须就绪）

1. **元数据基线**：核心库 ≥ 50 张高频表的字段字典与口径说明完成梳理（业务方配合）
2. **评测集种子**：50~100 条真实取数需求 + 正确 SQL + 正确结果
3. **权限方案确认**：与安全团队确认模拟身份查询与审计方案
4. **数据源与网络**：MySQL 数仓只读账号、网络连通、脱敏规则清单

## 6. 里程碑规划（12 周）

| 阶段 | 周期 | 交付物 | 门禁（Gate） |
|---|---|---|---|
| **G0 立项与调研** | W1–W2 | 用户访谈报告（5~10 人）、MVP 场景确认、章程评审通过 | 章程获业务与安全双方签字 |
| **G1 评测集与架构** | W3–W4 | 评测集 v1（≥50 条）、架构设计文档、权限方案评审通过 | 评测集通过业务方确认 |
| **G2 取数链路 MVP** | W5–W7 | Chat2SQL 端到端跑通（内部数据团队自用） | 可执行率 ≥ 90%（内部集） |
| **G3 校验与知识增强** | W8–W9 | SQL 校验器、口径库接入、元数据问答 | 可执行率 ≥ 95%，幻觉率 ≤ 2% |
| **G4 灰度试点** | W10–W11 | 单个业务部门灰度、巡检简化版上线 | 正确率抽检 ≥ 90%，无安全事件 |
| **G5 复盘与扩量** | W12 | 复盘报告、二期规划（质量巡检完整版/Excel 源） | 门禁全过 → 申请扩量 |

每个 Gate 未达标：修复优先于赶进度，允许顺延但需在周报中说明。

## 8. 风险登记（Top 5）

| # | 风险 | 等级 | 应对 |
|---|---|---|---|
| 1 | 错误数据误导决策 | 高 | 校验器 + 抽检门禁 + 结果页标注"AI 生成，需人工确认" |
| 2 | 元数据/口径缺失导致幻觉 | 高 | G1 前置治理，召回不到口径时明确拒答 |
| 3 | 业务口径频繁变更 | 中 | 口径库版本化管理，变更走业务接口人确认 |
| 4 | 数据权限/合规问题 | 高 | G1 安全评审一票否决；审计日志先行 |
| 5 | 用户期望过高（当万能客服用） | 中 | 明示负面清单；拒答话术模板化 |

## 9. 沟通与治理机制

- **周会**：进度 + 指标看板（可执行率/正确率/介入率趋势）
- **双周**：与业务接口人对齐口径与反馈
- **Gate 评审**：每阶段结束召开，业务 + 安全 + 项目三方参加
- **决策记录**：所有范围变更走书面变更单，更新本章程版本号
