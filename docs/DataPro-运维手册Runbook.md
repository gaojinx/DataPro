## 1. 监控与告警

### 1.1 告警项（Prometheus 规则）

| 告警 | 阈值 | 级别 | 首要动作 |
|---|---|---|---|
| API 5xx 率 | >5% 持续 5min | P1 | 查 Loki 最近错误 → 必要时停服开关 |
| 取数 P90 时延 | >45s 持续 10min | P2 | 看 LLM/DB 哪个节点慢 |
| LLM 调用错误率 | >10% | P1 | 查供应商状态页，切换备用模型 |
| 执行引擎连接池 | 使用率 >90% | P2 | 查慢查询，临时扩池 |
| Milvus 不可用 | 探活失败 | P2 | 确认降级生效（关键词召回） |
| 巡检任务失败 | 当日未产出 | P2 | 手动触发，查数仓连通性 |
| 幻觉率（日级统计） | >2% | P1 | 冻结 prompt 版本，回滚至上一版 |
| 令牌消耗异常 | 日消耗 >2× 均值 | P3 | 查是否有循环重试/滥用 |

### 1.2 看板

- Grafana：QPS / 时延分位 / 节点失败率 / token 消耗（按用户）
- 业务看板：可执行率 / 拒答率 / 👎 率 日趋势

## 2. 常见故障处理

### F1 LLM 超时/限流激增
1. 查供应商状态页确认是否平台故障
2. 是 → 切换备用模型配置（`MODEL_FALLBACK` 开关），重启 api 容器
3. 否 → 查最近 trace 是否存在异常重试循环，修 prompt 或限流参数

### F2 数仓连接耗尽
1. `SHOW PROCESSLIST` 查慢查询来源（是否 Agent 生成的大扫描 SQL）
2. 杀掉超过 10s 的 Agent 查询（有 trace 标记）
3. 临时降低执行并发上限（配置 `EXEC_MAX_CONCURRENCY`）
4. 若为某类问题集中触发 → 在校验器加扫描量阈值临时规则

### F3 Milvus 不可用
1. 确认降级自动生效（日志出现 `recall_degraded=true`）
2. 尝试重启 milvus 容器；不可恢复则保持降级运行
3. 降级期间召回质量下降，观察拒答率是否异常升高

### F4 审计写入积压
1. 审计为旁路异步，积压不影响主流程
2. 检查 MySQL audit_log 写入瓶颈，必要时批量 flush 间隔调小

### F5 全站异常
1. **先停服**：`feature.data_pro_enabled=false`（前端显示维护中）
2. 排查后恢复；停服动作本身记录到值班日志

## 3. 降级开关清单

| 开关 | 作用 | 默认 |
|---|---|---|
| `feature.data_pro_enabled` | 全站开关（一键回滚） | true |
| `feature.inspection_enabled` | 巡检开关 | true |
| `MODEL_FALLBACK` | 备用模型路由 | off |
| `recall.degraded_mode` | 强制关键词召回 | auto |
| `EXEC_MAX_CONCURRENCY` | 执行并发上限 | 20 |

## 4. 日常运维操作

| 操作 | 方式 |
|---|---|
| 查某次取数完整链路 | `/admin/audit` 输入 trace_id → 节点级回放 |
| 手动触发巡检 | worker 容器 `python -m inspection.run --table xxx` |
| 手动触发评测 | `POST /admin/eval/run` |
| 发布新 prompt | Git 合入 → CI 跑评测 → 部署（禁止热改） |
| 审计日志导出（合规检查） | `SELECT ... FROM audit_log WHERE ...` → CSV，双人复核 |

## 5. 值班与升级路径

- 灰度期：工作日值班 1 人（P1 响应 15min，P2 响应 2h）
- 升级：后端值班 → 后端 Lead → PM（涉及对外沟通/停服决策必须到 PM）
